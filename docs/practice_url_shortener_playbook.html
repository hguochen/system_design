Interview Playbook — The Flow + URL Shortener Model Answers

00 🗺️ How To Use This

Two documents fused into one. The left column of every phase is reusable — it applies to every system design question you will ever get. The right column is the URL shortener instance of it. When you start the rate limiter, you reuse the flow and swap the instance.

Read it once end-to-end. After that, only ever read §10 (Cheatsheet) and §11 (Failure Modes) before a mock.

⚠️ Do not read this immediately before re-attempting the URL shortener. Recognition feels like mastery and isn't. Attempt cold first, then diff your answer against this.

The one idea this document is built around

An interviewer is not scoring whether your architecture matches theirs. They are scoring whether, at every fork, you saw that it was a fork, named the options, and picked one for a stated reason. A design with a "wrong" choice and an articulated tradeoff scores higher than a "right" choice asserted without one.

02 1️⃣ Phase 1 — Requirements (5 min)

Reusable playbook

Open with this, always "Let me propose a scope and you can push back. I'll assume the core loop is [X] and [Y], and I'm going to explicitly leave out [Z] because it doesn't stress the interesting parts of the system. Does that match what you had in mind?"
Never open with this "What features are in scope? What's out of scope? Any other requirements I should know about?"

This reads as deferring the design to the interviewer. At L6 the ambiguity is the test — resolving it yourself is the thing being measured.

Four things you must extract or assert, in order:

  1. Functional scope — 3 to 5 features, no more. Anything else is explicitly deferred.
  2. Scale — DAU/MAU, and whether traffic is uniform or spiky.
  3. Non-functional targets, quantified — availability as a number of nines with its cost, latency as a percentile with a measurement point, consistency as a named model.
  4. Per-path SLA split — this is the L6 move most candidates miss. Different paths deserve different targets.
🎯 The per-path SLA split, stated generally: a path whose failure is retryable by the user can tolerate lower availability than a path whose failure breaks something already published into the world. Find that asymmetry in every problem.

URL shortener — model answer

Functional (in scope)

  • Authenticated user submits a long URL, receives a short URL
  • Anyone (no auth) resolves a short URL and is redirected
  • Owner views per-link click counts over a 1-year window
  • Links are revocable — needed for abuse and legal takedown

Out of scope (say the reason, not just the exclusion)

  • Custom aliases — same conditional-write path as generated codes, adds a namespace-collision discussion but no new distributed-systems problem. Happy to add if you want it.
  • Link editing — mutating a mapping after publication breaks the immutability property my whole cache strategy leans on. I'd rather treat it as revoke + recreate.
  • Malware/phishing scanning — real product requirement, but it's an async classification pipeline, orthogonal to the core system.
  • Non-HTTP schemes — HTTP/HTTPS covers effectively all demand.

Non-functional — with the per-path split

PathAvailabilityWhy
Redirect (read)99.99% → 52 min/yrA published link that 404s is permanently broken from the user's perspective. Failure is not retryable — it's visible to everyone who ever received that link.
Create (write)99.9% → 8.7 hr/yrA failed creation is retried in 2 seconds and nobody outside notices. Buying an extra nine here is spending on the wrong path.
Say this on the availability cost "99.99% is 52 minutes a year. Going to five nines takes that to 5 minutes, which means every dependency in the path also needs five nines and I need multi-region active-active with automated failover under a minute. That's a superlinear cost increase for a link shortener, so I'm consciously stopping at four."

Latency — and the physics trap

Target: p99 < 100ms, client-observed, end-to-end. You must immediately acknowledge what that forces:

Say this — it pre-empts the hardest requirements-phase probe "Client-observed p99 under 100ms globally is not achievable from a single region — Sydney to Virginia has a round-trip floor near 200ms on fiber, and that's before TLS handshakes. So the 100ms target is itself a design constraint: it forces me to terminate connections at edge PoPs near the user via anycast, and it means the redirect decision has to be servable close to the user rather than from one origin. I'm flagging that now because it shapes phase 4."
✅ This single paragraph converts a latency number into an architectural constraint. That transition is what separates a requirements list from requirements analysis.

Consistency

The mapping code → long_url is immutable once created. That is the most important property in the whole problem — it means the read path can be eventually consistent and aggressively cached without correctness risk. The one exception is revocation, which is why revocation gets special handling in §7.

Likely probe "Why does immutability matter to you?" → "Because it means a stale cache entry is never wrong, only potentially outdated in existence. I never have to invalidate on update, only on delete. That collapses my entire cache-coherency problem down to one narrow case."

03 2️⃣ Phase 2 — Estimation (5 min)

Reusable playbook

  1. State assumptions as assumptions. "I'll assume X — tell me if you'd rather I use a different number."
  2. Derive reads and writes independently. Do not assume a ratio and then back-solve one from the other — that's circular and interviewers catch it.
  3. Always compute peak, not just average. Use 2–5×. Provision against peak.
  4. Find the problem's one sizing constant. Every question has one: code length here; window size and counter cardinality for a rate limiter; shard count for a feed.
  5. Close by naming the binding constraint. "Storage is trivial, bandwidth is trivial, the constraint is X." This is the sentence that makes the whole phase worth doing.
💡 Use 105 seconds/day (86,400 ≈ 100,000) to divide in your head. Say out loud that you're rounding — precision theatre wastes time and rounding aloud reads as fluency.

URL shortener — model numbers

ASSUMPTIONS
  100M DAU
  10% of DAU create 1 link/day
  Read:write ≈ 100:1  (each created link is shared and clicked many times
                       over its lifetime — this is a link-distribution product,
                       not a link-creation product)
  Peak = 3× average
  Retention: modelled at 10 years (product promise is "forever")

WRITES
  10M links/day  ÷ 10^5 s  =    ~116 QPS avg   →   ~350 QPS peak

READS
  1B redirects/day ÷ 10^5 s = ~11,600 QPS avg   → ~35,000 QPS peak

STORAGE  (per row ≈ 500 B incl. index + overhead)
  10M/day × 500 B      =    5 GB/day
                       =  1.8 TB/year
                       =   18 TB/10 yr
  × 3 replication      =   54 TB      ← unremarkable; one rack

ANALYTICS
  1B click events/day. Raw retention is the trap: at 100 B/event that's
  36 TB/yr of raw events for a dashboard nobody queries at that grain.
  → Roll up to (code, day) counters:
     ~50M links with traffic/day × 30 B = 1.5 GB/day = ~550 GB/yr. Fine.

BANDWIDTH
  35K QPS × 500 B = ~17 MB/s.  Trivial. Not a constraint.

KEYSPACE  ← the sizing constant
  Codes needed over 10 yr = 10M × 365 × 10 = 36.5B
  62^6 = 56.8B  → 64% utilisation  ✗
  62^7 = 3.52T  →  1% utilisation  ✓
  → CHOOSE 7 CHARACTERS

LITTLE'S LAW  (concurrency, for server count)
  L = λW = 35,000 QPS × 10 ms = 350 requests in flight at peak
  At ~200 concurrent connections/server → ~2 servers of raw capacity.
  Provision ~15–20 across regions for N+2 redundancy, deploys, and
  regional failover — not for throughput.
⚠️ Why 7 and not 6 is a real answer, not a nitpick. If you generate codes randomly and check for collisions, retry probability scales with keyspace occupancy. At 1% full, collisions are negligible and a single conditional insert almost always succeeds first try. At 64% full, you're retrying constantly and your write latency distribution develops a long tail. The keyspace decision and the generation-strategy decision are the same decision.
Close the phase with this "So: storage is 54TB, which is unremarkable. Bandwidth is 17MB/s, which is nothing. Write QPS is 350, which one machine handles. The binding constraint is 35,000 read QPS at sub-100ms p99 globally — that's a latency-and-fanout problem, not a capacity problem, and it's what the rest of my design optimises for."
Likely probe "Your read:write ratio — defend it." → "It's an assumption about product behaviour, not a derivation. A shortener exists because links get distributed: one creation event fans out to a tweet, a newsletter, a QR code. 100:1 is the industry-observed range. If it were actually 10:1, my caching tier shrinks and the CDN stops earning its keep — so I'd want to validate this number before committing to the edge investment."

04 3️⃣ Phase 3 — API Design (3 min)

Reusable playbook

Three minutes, 2–3 endpoints. The API is where you quietly plant design decisions the interviewer will reward later: status codes, idempotency keys, pagination, auth boundaries.

POST /api/v1/urls
  Auth:    Bearer <token>  |  X-API-Key (business tier)
  Headers: Idempotency-Key: <uuid>      ← client retries don't create duplicates
  Body:    { long_url, custom_alias?, expires_at? }
  201 →    { code, short_url, created_at }
  409 →    custom_alias already taken
  400 →    malformed / non-http(s) scheme / exceeds 2KB

GET /{code}
  Auth:    none
  302 →    Location: <long_url>
           Cache-Control: no-store        ← see §7 for why this matters
  404 →    unknown code
  410 →    Gone (revoked)  ← distinct from 404 on purpose

GET /api/v1/urls/{code}/stats?from=&to=&granularity=day
  Auth:    Bearer, must own the link
  200 →    { series: [ { date, clicks }, ... ] }
Say this while writing it — it banks two points early "Two things I'm deciding here rather than later. First, 302 rather than 301 — I'll justify that in the deep dive, but it's driven by the analytics and revocation requirements. Second, an idempotency key on create, so a client retry after a timeout returns the existing code rather than burning a second one — otherwise every network blip permanently leaks keyspace."
💡 410 vs 404 for revoked links is a small detail that signals care: 410 Gone tells crawlers and clients the resource is intentionally and permanently removed, so they stop retrying. 404 invites re-crawling.

05 4️⃣ Phase 4 — High-Level Design (10 min)

Reusable playbook

  • Draw each request path separately. Never one tangled diagram.
  • Order matters: client → edge → LB → service → cache → store. Walk it in that order and narrate the request.
  • Flag your own hard component out loud. "The interesting part here is X — I'll come back to it in the deep dive." This buys you credit and steers the deep dive onto ground you've prepared.
  • Every component you draw must have a reason. If you can't say what it buys you, don't draw it.
🏗️ URL Shortener — Reference Architecture

Note the deliberate absence: the CDN does not cache redirect responses. §7 explains why that single decision resolves three separate problems at once.

Narrate the diagram like this "A redirect arrives at the nearest edge PoP by anycast — that's where TLS terminates, which is what buys me the latency target. The edge does not cache the redirect; it forwards to a regional LB and a stateless redirect service. That service checks an in-process LRU, then Redis, then read replicas. At ~95% combined hit rate only about 1,700 QPS ever reaches the store at peak, which is why a single modest cluster is enough. Writes are a completely separate, much smaller path — and the interesting component there is the key allocator, which I'd like to go deep on."

06 5️⃣ Phase 5 — Data Model + THE CRUX

Reusable playbook — engine choice

Derive it in this order, out loud. Never skip to the answer.

  1. Access patterns first. What queries must be fast? What's the read/write shape?
  2. Then schema. Fields, keys.
  3. Then engine, justified by the access pattern.
  4. Then partition key, and check it for skew.
Instant credibility loss "I'll use NoSQL because it scales." — Every interviewer has heard this a thousand times and it says nothing. NoSQL is not a thing; it's the absence of a thing.

URL shortener — data model

ACCESS PATTERNS
  1. Point lookup by code                      ← 35K QPS, must be <10ms
  2. Insert new code (must fail on duplicate)  ← 350 QPS
  3. Mark code revoked                         ← rare
  4. List links by owner                       ← rare, dashboard only
  No joins. No range scans on the hot path. No transactions across rows.

SCHEMA — urls
  code        STRING  PK / partition key   (7-char base62)
  long_url    STRING  (≤ 2 KB)
  owner_id    STRING
  created_at  TIMESTAMP
  expires_at  TIMESTAMP  NULL
  status      ENUM(active, revoked)
  UNIQUE constraint on code  ← load-bearing, see below

SCHEMA — clicks_rollup  (separate OLAP store)
  (code, date) → count

ENGINE
  A distributed KV store — DynamoDB, Cassandra, or a sharded MySQL
  used purely as a KV. Justification is pattern 1: the entire hot path
  is a single-key point lookup with no relational access. I am paying
  for nothing I don't use, and I get linear horizontal scaling on the
  partition key for free.

  Secondary index on owner_id for pattern 4 — it's off the hot path,
  so an eventually-consistent GSI is fine.

PARTITION KEY = hash(code)
  Codes are uniformly random ⇒ no key skew by construction.
  Note: this does NOT prevent a hot *link*. One viral code is a hot-key
  problem, not a partitioning problem, and it's solved by the L1 cache
  absorbing it — not by resharding.
🎯 That last paragraph is a free point. Distinguishing key skew (fixable by partitioning) from access skew (fixable only by caching) is a distinction most candidates blur, and it directly connects to your topic 7.6 and 5.7 material.

⭐ THE CRUX — where the short code comes from

⚠️ This is the single highest-leverage question in this problem. In your first mock it was asked five times and never answered, and that alone accounted for two grade points. Lead with it unprompted.

First, the impossibility argument — say this before proposing anything

The sentence that resolves the whole problem "Uniqueness cannot come from the URL's content. Mapping an unbounded input space into 627 outputs is a pigeonhole argument — collisions are mathematically guaranteed for any content-derived function. If instead I make the function lossless to avoid collisions, the output length grows with the input and I haven't shortened anything. So the code has to come from either a coordinated allocator or a conditional write. Those are the only two families."
🔀 Code Generation — The Decision Tree

The four options, priced

ApproachMechanismBuys youCosts you
Hash + truncate MD5/SHA of URL → base62 → take 7 Identical URLs dedupe for free; fully stateless Collisions guaranteed; needs salt-and-retry and a conditional write anyway — you pay the cost without escaping it
Counter + range lease ZK/etcd hands each server a disjoint 1M block; server increments in-memory Zero collisions structurally; no per-write coordination; dense keyspace use Sequential ⇒ trivially enumerable; needs a coordinator; dead servers waste ranges
KGS (pre-gen pool) Offline job generates unused random codes into a table; servers lease blocks of 10k Non-enumerable and zero per-write coordination A whole extra service with its own HA and used/unused bookkeeping
⭐ Random + conditional insert 7 random base62 chars → INSERT ... IF NOT EXISTS → retry on conflict No coordinator, no extra service, non-guessable, ~0 retries at 1% occupancy One extra write round-trip; degrades as keyspace fills (mitigated by choosing 7 chars)
Model answer — deliver it in this order "I'll go with random 7-character codes plus a conditional insert. At 1% keyspace occupancy the collision probability per attempt is about 1%, so almost every write succeeds first try, and I get non-enumerability for free — which matters because people shorten private documents.

The alternative I seriously considered is counter ranges leased from ZooKeeper. It's strictly better on collisions — zero by construction rather than probabilistically zero. I rejected it because it produces sequential codes, which lets an attacker walk the entire database with a for-loop, and because it adds a coordinator to my dependency graph.

If I later found the retry rate climbing as the keyspace filled, I'd move to a pre-generated key service, which gets me both properties at the cost of running one more thing."

The availability question — always asked next

Probe: "What happens to your 99.99% when the allocator dies?" For random + conditional insert: there is no allocator. That's the point — the failure mode doesn't exist. Uniqueness is enforced by the storage engine, which I already depend on.

For counter ranges: servers keep serving from their leased block. ZooKeeper being down only matters when a server exhausts its million codes — hours away at 350 QPS. This is why you lease ranges instead of calling a counter per write: it converts a hard synchronous dependency into a soft one with hours of slack. Say this sentence — it's the actual insight behind range leasing.

Atomicity — the race condition, answered properly

Not an answer "We check the DB again just before writing." — This is the race, relocated. Two workers can both check, both see nothing, both write. Moving the check later in the pipeline doesn't make check-then-write atomic.
The answer "I make the check and the write a single indivisible operation at the storage engine, so there is no window between them:
  • INSERT ... ON CONFLICT DO NOTHING against a unique index (Postgres/MySQL)
  • ConditionExpression: attribute_not_exists(code) (DynamoDB)
  • SETNX (Redis)
  • Lightweight transaction / IF NOT EXISTS (Cassandra — but note this costs a Paxos round and is far more expensive)
One round trip. The loser gets a conflict response, generates a new random code, and retries. At 1% occupancy that happens roughly 1% of the time."
💡 Transferable rule: whenever you catch yourself saying "check, then write," stop — you have described a race. The fix is always to push the check into the write as a conditional operation, never to add a queue or a lock in front of it.

07 6️⃣ Phase 6 — Deep Dives (15 min)

🎯 This phase decides your grade. Structure every answer as mechanism → failure mode → mitigation → cost, and volunteer the failure mode before you're asked for it.

Deep dive A — 301 vs 302 (the decision that unlocks three requirements)

301 Moved Permanently302 Found

Server loadDrastically lower — the browser does your workFull 35K peak QPS lands on you

Model answer "302, with Cache-Control: no-store. I committed to per-link analytics and to 5-second revocation, and a 301 makes both of them structurally impossible — not hard, impossible, because the request never leaves the browser. The cost is that I absorb the full read volume instead of letting browsers absorb it, which is precisely why I sized the cache tier the way I did in phase 4. If the requirements had been 'maximum performance, no analytics, no takedown,' 301 would be the better answer."
⚠️ The trap you fell into in mock #1: you correctly observed "I can't count 301 redirects because the browser does it without my knowledge" — and then treated that as an external constraint to work around. It was your own design parameter. Whenever you notice yourself saying "there's no way I can…", check whether the thing blocking you is something you chose.

Deep dive B — the caching tier, with the specifics interviewers demand

"We'll use a cache" is worth zero. These six answers are what it's actually worth:

QuestionAnswer
What's cached?code → long_url. Immutable until revocation, which makes it an ideal cache candidate — there is no update path to invalidate on.
Where?L1 in-process LRU (~10k hottest codes/server, absorbs viral spikes with zero network hops); L2 Redis cluster holding the full active working set.
How big?Assume ~100M links active in any window × 500 B ≈ 50 GB. Comfortably a modest Redis cluster; no need for anything exotic.
Eviction?LRU, not LFU. Link popularity is sharply time-decaying — a link is viral for 48 hours and then dead forever. LFU would keep 2019's most-clicked link resident while evicting today's active one. Match the policy to the access-pattern's shape, not to what sounds sophisticated.
Hit rate?~95%. Access is strongly Zipfian — a small head of links takes the overwhelming majority of clicks. At 95%, only ~1.7K QPS of the 35K peak reaches the store.
On miss?Read replica → populate both tiers. Critically: request coalescing / singleflight, so 10,000 simultaneous misses on one newly-viral code produce one backend read, not 10,000. Without it, a link going viral is a self-inflicted DDoS.
Negative caching?Cache 404s for ~60s. Otherwise anyone enumerating the keyspace sends every miss straight through to your database — the cache stops protecting you exactly when you're under attack.
💡 Request coalescing and negative caching both come directly from your topic 5.6 and 5.7 material. Naming them by name — "singleflight," "thundering herd" — is cheap, high-signal vocabulary.

Deep dive C — revocation in 5 seconds across four cache layers

The instinct is to shorten every TTL to 5 seconds. Do the arithmetic on that before you say it:

⚠️ Why the TTL answer is wrong. A 5-second TTL means every cached entry expires 17,280 times a day. Your hit rate collapses toward zero, your origin absorbs nearly the full 35K QPS, and you are now paying for a cache tier that does nothing. You cannot solve a push problem by shortening a pull interval — you've made the cache useless without even hitting the target, because a 4.9-second-stale entry still serves a revoked link.

Model answer — layer by layer "TTL is the wrong tool here because it's pull-based; I need push. Concretely:

1. Primary store — write status=revoked synchronously. This is the durable source of truth and it's the only strongly-consistent step.
2. Redis (L2) — issue a direct DEL on the key. Sub-10ms, not a TTL expiry.
3. L1 in-process caches — publish the revocation to a pub/sub topic every server subscribes to. Each server evicts its local entry on receipt. Sub-second fan-out across the fleet.
4. CDN — this is the one I can't push to reliably; purge APIs take 5–60 seconds, which blows my SLA. So I don't cache redirect responses at the CDN at all. I use the edge for anycast termination, TLS, and DDoS absorption — not for caching the redirect decision.

Worst case is 1–2 seconds, comfortably inside the SLA."
✅ Notice the elegance to point out explicitly: "not caching redirects at the CDN" resolves three problems at once — it makes 5-second revocation achievable, it makes analytics complete, and it removes an entire cache-coherency layer. Say that out loud. Recognising when one decision collapses three problems is exactly the judgment L6 is looking for.

Replication lag — the follow-up

Probe: "You wrote to the primary. Your reads come from replicas. Cross-region lag can exceed 5 seconds. How is your SLA still met?" "Because the invalidation path doesn't traverse replication at all. The pub/sub fan-out and the Redis DEL are pushes that go directly to the caches — they don't wait for the write to propagate through the replica topology. Replication lag only affects a request that misses every cache layer and lands on a lagging replica, which is a narrow window. If I needed to close it completely, I'd keep a small revoked-set — a Bloom filter of revoked codes, a few MB — replicated on the same fast push channel and consulted before serving. That's cheap because revocations are rare."

PACELC — say it in these words

Model answer "System-wide I'm PA/EL: during a partition I keep redirecting even if a replica is stale, because a stale redirect for an immutable mapping is harmless; and in normal operation I choose latency over consistency, which is what the whole cache hierarchy is. Revocation is a deliberate carve-out to PC/EC — legal correctness outranks availability on that path. But I implement the carve-out as a push invalidation rather than by raising consistency levels, so I don't pay the latency tax on the 99.999% of requests that involve no revoked link at all. That's the design point: scope the strong-consistency requirement to the narrowest possible path."

Quorum math — if they push on the replication model

If using a Dynamo-style store with N=3 "Redirects read at R=1. R+W>N is unnecessary for an immutable mapping — a stale read can only mean 'not created yet,' never 'wrong destination,' and it buys me one-replica latency. Writes go at W=2 so a single node loss can't lose a mapping — losing one permanently breaks a published link, which is my highest-severity failure. So W=2, R=1: I'm explicitly not quorum-consistent on reads, and that's a deliberate choice justified by immutability, not an oversight."

08 7️⃣ Curveballs & Wrap

Reusable playbook — how to take a curveball

  1. Do not re-architect. The test is whether your design absorbs change, not whether you can start over. Panic-redesigning is the failure mode.
  2. Name what breaks first. Re-run the binding-constraint analysis under the new condition.
  3. Say what stays the same and why. Explaining why most of your design is unaffected demonstrates you understood your own coupling.
  4. Price the fix. Every adaptation costs something. Name it.
CurveballModel response
"10× the traffic — 350K read QPS" Cache tier scales horizontally (more Redis shards, more app servers with L1). DB shards linearly on hash(code) — uniform keys mean no rebalancing pain. Key allocation is unaffected: at 3.5K write QPS a leased 1M block still lasts hours. The analytics pipeline strains first — 10B events/day — so I'd sample or pre-aggregate at the edge. Naming what doesn't break is as valuable as naming what does.
"Redis cluster is down" L1 absorbs the head of the distribution — probably 60–70% of traffic — so this is a degradation, not an outage. The remainder stampedes the replicas, so request coalescing is what saves me. I'd add a circuit breaker so a slow Redis doesn't consume every app-server thread waiting on it: fail fast to the replica rather than queueing. That's Little's Law in reverse — if W rises and λ is fixed, L grows until you exhaust connections.
"ZooKeeper is down" (if you chose counter ranges) Writes continue from already-leased ranges. Impact begins only when a server exhausts its million codes — hours at 350 QPS. Range leasing exists precisely to convert a synchronous dependency into one with hours of slack. Meanwhile reads are entirely unaffected — the read path has no dependency on the allocator.
"A single link goes viral — 1M QPS on one code" This is a hot key, not a hot partition — resharding does nothing because it's one key. The L1 in-process cache is the answer: after one miss per server, every subsequent hit is served from local memory with no network hop. It gets better under load, not worse. If a single server still saturates, that's a fleet-size problem, not a data problem.
"Add custom aliases" Same conditional insert, same unique constraint — the mechanism is unchanged, which is the point. New concerns: a reserved-word blocklist (/admin, /api), a length floor so customs don't collide with the generated 7-char space, and 409 on conflict. I'd consider a separate namespace prefix to keep the two spaces disjoint entirely.
"Links must expire" expires_at column, lazy check on read (return 410 if past), plus a background sweeper for reclamation. Don't rely on the sweeper for correctness — lazy check is the correctness mechanism, the sweeper is only a storage optimisation.
"Support 99.999%" Push back before agreeing. That's 5 min/yr — it requires multi-region active-active, sub-minute automated failover, and every dependency in the path also at five nines. For a redirect service I'd ask what business outcome justifies roughly an order of magnitude more spend. Pushing back on a requirement with a cost argument is a positive signal, not insubordination.

The wrap (2 min) — script it

Close with this shape "To summarise: the binding constraint was global read latency, not capacity, so the design is a cache hierarchy in front of a KV store, with code allocation deliberately decoupled from URL content.

Remaining single points of failure: the Redis tier is a degradation rather than an outage thanks to L1; the primary store is the real one, mitigated by multi-AZ with automated failover.

What I'd monitor: cache hit rate by tier, conditional-insert retry rate as a leading indicator of keyspace pressure, and p99 redirect latency segmented by region — a global p99 hides a bad region.

09 ⚖️ Tradeoff Phrasebook

Your lowest-cost grade improvement. You already reason this way — the 99.99%-vs-99.999% answer in mock #1 proved it — but you only surface it when asked. Say these unprompted, five or more times per interview.

Pattern 1 — the default "I'm choosing X over Y because [constraint]. The cost is Z. I'd revisit if [condition]."
Pattern 2 — when the rejected option is genuinely good "Y is strictly better on [dimension A]. I'm still taking X because [dimension B] is what this SLA is actually about, and B dominates here."
Pattern 3 — pre-empting the probe "The failure mode of this is [F]. I'd catch it with [signal] and mitigate with [M]."
Pattern 4 — bounding your own confidence "I'm least confident about [X]. My assumption is [A]; if that's wrong the design changes in [specific way]."
Pattern 5 — scoping a hard requirement down "Rather than making the whole system [expensive property], I'm scoping that requirement to [narrow path] and leaving everything else on the cheap path."
💡 Pattern 5 is the highest-scoring one and it's what the revocation answer in §7 is an instance of. Narrowing a costly requirement to the smallest path that actually needs it is a recognisable senior move — look for an opportunity to use it in every design.
