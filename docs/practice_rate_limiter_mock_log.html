Rate Limiter — Mock Interview Log (1B DAU / 1M QPS)

00 🗺️ Summary & Verdict

⚖️ Verdict: solid on the transferable Phase B discipline, shaky on the rate-limiter-specific core. Requirements and estimation skills clearly carried over from the URL shortener; the distributed-counter design — the heart of this problem, and heavy Topic 25 territory — is where the foundation ran out. This was a transfer test, and it did its job: it confirmed the roadmap gap (Problem #2 depends on Topic 25, which is unstudied) is real.

This mock was run deliberately at Phase B scope — using only stateless-service, load-balancing, caching, and sharding primitives, treating the rate-limiting algorithm internals as named tradeoffs rather than implemented depth. That framing is why the requirements/estimation phases went well and the core counter architecture wobbled: the counter model is the Topic 25 content.

The one-line takeaway

🎯 The canonical rate-limiter counter design is shard by key + atomic INCR + a local blocked-key cache for hot keys. The interview went sideways when a more complex, approximate "slice-and-sync" design was chosen over this and defended with benefits it doesn't actually provide.

Did wellClean L3/L4→CDN, L7→gateway layering (Phase B CDN transfer). Good NFRs; accepting a 5% approximation buffer to buy latency is exactly the right instinct.

The fail-open / fail-closed exchange (the hardest call)

InterviewerMixed public API — mostly ordinary reads/writes, a few sensitive (login, token, payment). When the limiter's datastore is unreachable, fail open or closed? One global choice or per-endpoint? Commit + justify, including what it does to your 99.99% if you get it wrong.
Failure — inverted the mappingGary first proposed: ordinary → fail closed, sensitive → fail open. Backwards.
Interviewer — the scenario that exposed it"Redis is down 8 seconds. Under your scheme, your /login endpoint now has NO limit (fail-open) — what does a credential-stuffing bot do with those 8 seconds? And your ordinary reads all return 429 (fail-closed) — so your main API is dark because a cache node blipped. You've turned a protective add-on into a SPOF. Comfortable with both?"
Recovery — corrected under pushbackOrdinary → fail open (a protective component must never become the SPOF that takes down what it protects); sensitive → fail closed (an unprotected window on login/payment invites irreversible harm). Stated the general principle: default fail-open, pay the fail-closed cost only where over-allowing is irreversible.

04 3️⃣ Phase 3 — High-Level Design

InterviewerRequest path, sharding, atomicity of check-and-increment, algorithm choice (name the tradeoff even without the internals).
Gary — design (from diagrams)Gateway → cluster of Redis nodes, each holding a slice of the allowance, + a separate central Counter Store synced every 1s (aggregate ÷ N per node). Sharding by hash(user_id) / hash(IP) on consistent hashing. Over-limit: non-critical → 429 reject; critical → queue. Algorithm: fixed window; 5% buffer absorbs boundary burst + "race conditions where nodes read stale counts."
Failure — two contradictory designs at onceYou can't both (a) shard by hash(user_id) — key on one node, node holds the full count — AND (b) have each node hold a slice synced from a central store every 1s. Slicing only makes sense if a user's requests spread across all nodes, which contradicts sharding by key.
InterviewerWhich is it? And in the shard-by-key design, name the atomic primitive. The race you're buffering against is self-inflicted by the slice scheme.
Gary — doubled downSwitched the shard key to hash(request_uuid) so requests scatter across all nodes and each node holds a slice. (Chose the approximate design over the exact one.)
Interviewer — laid the two side by sideShard by hash(user_id): key on one node, one atomic increment, exact count, no central store, no sync, no race. Shard by hash(uuid): forces a central store, 1s staleness (huge at 1M QPS), divide-by-N unfairness (unlucky node rejects what a neighbor would allow), an extra tier. "You moved toward option two — defend it, or take the simple one. And name the atomic primitive (asked 2×)."
Gary — justification + primitiveJustified slice-and-sync by "durability + horizontal scaling + node-failure tolerance (9 slices survive)." Primitive = INCR / INCRBY.
Final correctionPrimitive ✓ — INCR is right for fixed window (atomic, returns new value; add EXPIRE to reset the window; Lua for multi-step algorithms). Justification ✗ — durability & horizontal scaling do not distinguish the designs: shard-by-key gets HA from per-shard replication and scales via the consistent hashing already drawn (topic 7.4). Worse, the slice design added a central counter store every node hits every second — a new SPOF/bottleneck. The one real reason to spread a key (the hot key: one abuser hammering a key at 100K/sec slams its single shard) went uncited — and its cheap fix is a local blocked-key cache, not rebuilding the counter model.
⚠️ Over-limit behavior note: "queue the request for critical APIs" is risky at 1M QPS — holding synchronous connections consumes the very resources you're protecting. Standard is 429 + Retry-After. (Also: over-limit behavior and limiter-failure behavior are two different axes — don't conflate them.)

05 ⭐ The Central Lesson — Counter Architecture

Everything in this mock rotated around one decision: how the distributed counter is structured. Two families exist; the interview went sideways by mixing them and then picking the harder one for the wrong reasons.

CANONICAL RATE-LIMITER COUNTER DESIGN (memorize this)

  1. SHARD the counter store by the rate-limit key:
       hash(user_id:api)  or  hash(ip:api)  →  one shard
     Each key lives on exactly one node ⇒ NO cross-node coordination.

  2. ATOMIC check-and-increment on that one node:
       INCR key            (atomic, returns new count)
       if new == 1: EXPIRE key    (reset the window)
       if new  > limit: reject 429 + Retry-After
     Multi-step algorithms (sliding window, token refill) ⇒ Lua script.

  3. HOT KEY defense (one abuser hammering one key):
       once a key is over its limit, cache "blocked" in-process at the
       gateway for a short TTL ⇒ stop hitting Redis for it entirely.
     Cheap. Keeps the exact design. No slice/sync rebuild needed.

  4. FAILURE posture:
       ordinary endpoints  → FAIL OPEN  (never let the limiter be the SPOF)
       sensitive endpoints → FAIL CLOSED (login/payment: block > over-allow)

  5. ACCURACY: a small over-allow (5% buffer) is almost always fine —
       admitting that unlocks the cheap designs. Ask the interviewer.
💡 Reflexes that would have saved this run: (1) When you shard by key, there is no cross-node race — don't buffer against a race your architecture created. (2) Before choosing the complex design, ask "does the simple one have the same benefit?" — durability/scaling did. (3) A protective component must never become a SPOF (the fail-open principle) — same idea recurs in the hot-key cache.

06 🔀 Transfer Test Result

This mock doubled as a test of whether shortener concepts transfer to an unrehearsed problem. The result was informative:

What transferred cleanly ✅

  • Requirements discipline — proposing scope, quantified NFRs, the availability cost argument, and the per-endpoint failure split (after one correction).
  • CDN / edge layering — the L3/L4-vs-L7 split reused Phase B CDN knowledge directly.
  • Estimation framing — spotting the write-heavy nature and that throughput, not memory, is the constraint (the same "which number is actually hard?" reflex from the shortener).
  • The atomic primitive concept — CAS/atomic-write from the shortener's Q2 reappeared as INCR (though it took two prompts to surface).

What did NOT transfer ❌

  • The distributed-counter architecture — the rate-limiter-specific core. Shard-by-key vs. sloppy-counter, hot-key handling, and the algorithm internals are Topic 25 content, and their absence showed exactly where the design tangled.
  • Volunteering failure modes — still the recurring habit gap: the hot key and the self-inflicted race both needed prompting.
✅ Net: the general interview method is now portable across problems — that's real and it's the point of the drilling. The rate-limiter content gap is specific and studyable (Topic 25, ~4h).

07 📚 Study Takeaways

  1. Study Topic 25 before the next rate-limiter attempt. This run empirically confirmed the "After Phase B" unlock is partial. Needed: the four algorithms (token/leaky bucket, fixed/sliding window), distributed counter consistency, hot-key handling, and rate-limit headers.
  2. Memorize the canonical counter design in §5 — shard-by-key + atomic INCR + local blocked-key cache. It's the answer this mock was missing.
  3. Carry the fail-open/closed principle forward — it's reusable in any protective component: default to preserving availability; fail closed only where over-permitting is irreversible.
  4. Failure-mode reflex — for every component drawn, say "and when this fails / when one key is hot, X happens" before being asked. Still the #1 recurring gap across both problems.
